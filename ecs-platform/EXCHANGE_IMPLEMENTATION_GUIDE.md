# Exchange implementation checkpoint

Source: build specification §7.7 and REQ-33. A linked return creates a **new** replacement reservation/order and leg, with intact delivered history, typed local payment evidence and ordinary fulfilment. Pre-payment/awaiting-Fynd cancellation and demo hold expiry now reconcile independent simulator outcomes before stock release. Formal callbacks, explicit declines and broader exchange policies remain open.

## Implemented locally

- Return details in both authorized fulfilment portals offer **Explore exchange variants** and **Preview replacement**. Only same-company, partner, market, brand, category and non-empty parent-style sibling variants are listed. Another partner's variant is not exposed even to an operator through this exchange route.
- `GET /api/v1/returns/:id/exchange-options` returns up to 50 variants and an explicit truncation flag. Listing does not imply sellability. `POST /api/v1/returns/:id/exchange-preview` validates the current return version, original delivered line, replacement relationship and UAE/AED scope. Standard session, role, CSRF and tenant/partner/market guards apply.
- Replacement routing uses the **same read-only planner** as actual order ingestion. Product sales status, partner activity, brand rights, ERP/Fynd/SFCC publication receipts, local mock mapping read-back, effective commercials, location eligibility, service area, cut-off, capacity and local ATP are checked. It does not bypass missing evidence because the seed says PUBLISHED. Local ATP is not proof of fresh live Fynd inventory.
- Normal intake recomputes the plan inside its existing serializable reservation transaction. Preview does not reserve and is not a reusable authorization token. It returns product/sales/return/inventory revisions for explanation, not permission to reuse stale stock.
- The preview makes **no business writes**: no new order, reservation, outbox job, ledger entry, audit decision or change to the delivered line/return. Saving a request and starting replacement checkout are separate explicit actions.

## Persistent requests, ATI decisions and pre-order cancellation

- `GET/POST /api/v1/returns/:id/exchanges` lists or saves a scoped request for ATI review. Saving requires an eligible preview, a reason and explicit acceptance of its provisional policy and full replacement price. The server recomputes eligibility inside the serializable transaction and checks product/sales/return revisions and price. It does not trust a stale browser quote.
- Migration 030 retains immutable ownership, original return/replacement identity, quantity, price and full preview snapshot. One active request per return is enforced by a partial unique index. Exact actor/request-key retries return the same record; changed payloads conflict. A cancelled key never silently creates a new request.
- `POST /api/v1/exchanges/:id/cancel` requires the pending version and a reason. A reasoned cancellation is retained with its actor/time; its exact retry is idempotent. The database prevents deletion, evidence edits and invalid transitions. Create/cancel audit failures roll back the transaction.
- Migration 031 extends requests with an immutable ATI decision. `POST /api/v1/exchanges/:id/review` accepts approve/reject, expected version and a required reason. Only ATI super administrators/operations managers may decide; vendor and unrelated ATI roles are denied. Approval recomputes current refund/catalogue/mapping/commercial/routing/stock gates while preserving accepted product/sales revisions and price. Changed accepted terms require rejection/cancellation and a newly accepted quote, not an operator price override.
- Review retains actor, time, action, reason and an additional approval-time quote separately from the original accepted snapshot. Rejection remains available when eligibility has changed and releases the active-request slot. Exact actor/action/version/reason retries return the recorded decision; conflicting decisions fail. Concurrent approval/cancellation has one winner. Audit failure rolls back the decision.
- States are REQUESTED → APPROVED or REJECTED; REQUESTED/APPROVED → CANCELLED is allowed only before any replacement order is linked. Cancellation preserves the ATI decision, including its approval snapshot. SQL guards reject partial decisions, history edits, deleted evidence and reversed decisions. Rejected/cancelled request keys cannot silently create a new request.
- Approval is labelled **Approved · awaiting replacement checkout**, never paid or exchanged. Approval itself does not change original delivery, return, inventory, ledger or outbox records. Cancelling a pre-order request releases the active-request slot, not stock, because none was reserved.
- Fresh seeds now use a distinct valid GTIN and canonical size-L identifiers, with DRAFT status and no fabricated publication receipts. Existing presenter catalogue rows are preserved, not reseeded.

## Explicit provisional demo pricing

`REFUND_AND_REPURCHASE_DEMO_V1` requires the original return to be closed with an acknowledged refund before replacement creation could proceed. Rejected, unrefunded and already-linked cases are blocked. A separate current-price purchase belongs to SFCC/ATI; original vendor/operator discounts are not automatically copied. The arithmetic difference is informational, **not** a second refund or a net charge instruction.

Example: original gross AED 1,850 less AED 100 vendor discount and AED 50 operator discount gives an original refund of AED 1,700. A size-L replacement at AED 1,850 has an informational difference of AED 150, but the proposed flow consists of the existing AED 1,700 refund and a separate AED 1,850 SFCC-owned purchase. Equal and lower replacement prices are also calculated using decimal arithmetic.

This is a labelled demonstration rule, not an approved ATI commercial policy. Production must resolve refund-versus-credit, discount retention, price protection, payment authorization/capture timing, refund failure and replacement cancellation policy.

## Separate replacement checkout and fulfilment

- ATI operations explicitly records a reason and **simulated** customer acceptance before `POST /exchanges/:id/checkout`. This is not evidence of actual customer consent or a real charge. Demo-only and existing operational destination guards prohibit live dispatch.
- The serializable transaction rechecks approved product/sales revisions, price, original refund and all routing gates. It creates one new `ECS-EX-…` order, reserves stock, creates an `AWAITING_PAYMENT` leg, records immutable execution identity and links `ReturnCase.replacementOrderId`. The original order/delivery/refund are not rewritten. Any failure rolls back all these writes and queued jobs.
- Migration 032 retains the accepted amount, request fingerprint, owner, new order and payment intent. Exact concurrent checkout retries return one execution; changed retries conflict. The old request-cancellation command cannot cancel a linked order.
- A durable `purchaseExchange` job uses the strict local SFCC v1 payload/receipt contract in `packages/contracts/exchange-payment.ts`. Ownership, intent, order, amount, policy and CAPTURED status must all match. Only then are the order/leg advanced to `AWAITING_FYND` and the new Fynd order queued. This contract describes our simulator, not an official SFCC/Fynd endpoint.
- Transport failures, invalid receipts and acknowledgement-transaction failures retain the reservation and payment hold. Retry/dead-letter/replay reuse one remote simulator purchase and one local order. No fulfilment is released from generic HTTP success or an incorrect amount. Pending holds now enter the cancellation workflow at their provisional 30-minute demo-clock deadline.
- The new Fynd mock order/shipment then follows existing accept → pick → pack → dispatch → delivery commands. Dispatch consumes the replacement stock, and delivery appends its own line-level financial events; original delivery and return evidence remain separate.
- Cancelling an assigned/accepted/picking replacement uses the ordinary Fynd shipment command. Only acknowledged cancellation releases reserved stock and queues a separate `refundExchangePurchase`. Payment remains `REFUND_PENDING` through failures until a matching REFUNDED receipt is retained. It does not create a fictitious delivered sale or vendor reversal for an undelivered replacement.
- Both authorized portals show the retained execution, full separate charge, payment/refund receipts and a link to the new shipment. ATI owns checkout initiation. Request/approval snapshots still describe their own earlier no-reservation state, not the current execution.

## Cancellation before fulfilment and payment-hold expiry

- `POST /api/v1/exchanges/:id/checkout/cancel` is restricted to ATI fulfilment roles, scoped by company/market, CSRF protected and requires the current execution version and a reason. It accepts only payment-pending, awaiting-Fynd or assigned legs with no command already in flight. Once a leg is accepted, use the existing shipment cancellation workflow. Vendors can inspect their own cancellation evidence but cannot initiate this operator action.
- Migration 033 retains immutable cancellation intent, actor, reason, cause, payload and acknowledgement receipts. Exact concurrent retries return one intent. Changed requests conflict. The checkout's immutable hold deadline is thirty demo-clock minutes after creation; this is a provisional demo policy, not an ATI-approved payment timeout.
- Requesting cancellation invalidates unfinished purchase/order/shipment jobs and their leases. Their retained `CANCELLED` records cannot be replayed. A response from a worker that lost its lease cannot advance local state. Reservations remain held and original deliveries/returns are unchanged.
- Two durable, strictly typed local operations (`SFCC cancelExchangePurchase`, `FYND cancelExchangeOrder`) obtain independent outcomes. Simulator-owned rows serialize capture/create against cancellation, preserving any earlier purchase receipt and preventing new capture/order/shipment creation after cancellation. They do not infer remote success from ECS status. Earlier simulator receipts are carried forward when establishing a fence for older executions.
- SFCC reports either VOIDED (no captured purchase) or CAPTURED with the original exact purchase receipt. A lost local capture acknowledgement is recovered from this evidence. Fynd separately confirms the replacement is fenced. Only both acknowledgements permit atomic reservation release, cancelled legs/order and inventory propagation.
- A captured charge then uses the existing separate refund job; cancellation remains `REFUND_PENDING` until its typed refund acknowledgement. A prevented purchase completes without a fictitious refund. Cancellation/refund failure remains visible in retry/DLQ with audited replay; malformed identity/amount receipts do not release stock.
- Both worker transports invoke a bounded hold sweep before polling dispatch. Only still-PENDING expired holds enter this same workflow; a captured payment does not expire. Concurrent sweeps deduplicate. PostgreSQL polling is exercised locally; Redis/BullMQ runtime remains unverified.
- Both portals show the deadline, reason, payment outcome, Fynd acknowledgement and completion/refund status. The provisional policy uses the demo clock, not elapsed presenter wall time. It never moves real money or contacts real Fynd.

## Verification and remaining work

`tests/integration/exchange-preview.test.ts` uses isolated PostgreSQL fixtures, actual local mapping/publication mock jobs and 42 cases. A historical refunded delivery is an explicit precondition, not claimed evidence of a new refund journey. Checks cover M→L pricing, read-only invariants, identity boundaries, stale/malformed inputs, workflow blockers, equal/lower pricing, exhausted stock also rejected by normal intake, publication/mapping gates, parent-style identity and concurrent previews. Request/review checks cover competing/exact concurrent submissions and decisions, price/version drift, actual pause/restore sales-revision drift, audit rollback, SQL immutability, partner/role/CSRF boundaries, API restart persistence and idempotent cancellation with retained approval evidence. Checkout cases cover atomic reservation/linkage, full new-leg delivery with AED 1,850 sale and AED 518 commission, payment failure/DLQ/replay, remote-success/local-rollback recovery, malformed amount denial and assigned-leg cancellation/refund. Cancellation cases additionally prove no release before both acknowledgements, immutable intent/fences, enqueue rollback, lost capture/order acknowledgements, independent refund recovery, remote concurrent capture/void, expired hold deduplication, forged receipt rejection and lost-lease purchase/shipment responses. Three unit cases validate strict purchase/refund/cancellation contracts.

The connected browser tests first request a return from the genuinely delivered Maison Azure leg and show missing-refund and unpublished-size-L blockers without mutations. ATI submits, approves and publishes size L through actual local mock acknowledgements and completes the size-M Good-QC refund. Request/review/cancellation scenes retain history without moving stock. The added eighth connected scene then obtains renewed approval, starts the separate simulated checkout, reloads its typed payment evidence and follows the new shipment into vendor fulfilment and ATI delivery. Read-only comparisons prove original delivery/refund preservation, the return/new-order link and exact size-L stock movement at Dubai Mall. Screenshots were reviewed for legible receipt/amount/order links and routing/delivery evidence. This is not comprehensive responsive/Arabic/accessibility or payment-recovery browser acceptance.
