# Isolated browser acceptance

Run from `ecs-platform`, with the local PostgreSQL server already running:

```sh
PLAYWRIGHT_BROWSERS_PATH=.local/browsers pnpm exec playwright install chromium
pnpm test:e2e
```

The first command downloads the matching browser into the ignored project-local cache. The second creates a new `ecs_e2e_<random UUID>` database on the loopback PostgreSQL server from `TEST_DATABASE_URL` or `.env`'s `DATABASE_URL`. It never seeds, truncates or drops `ecs_demo` or `ecs_test`. The database user needs local CREATE DATABASE permission. Remote database hosts and production mode are refused before startup.

## What the runner owns

- An exclusive `.local/e2e-run.lock` prevents competing runs. Ports 3002 (web), 4002 (API) and 4102 (mock systems) must be free; the runner does not kill unrelated listeners or reuse the presenter preview.
- All migrations are applied to the newly created database, then the fictional seed is loaded. Maison Azure, Lumera and Northline brand/location mapping preparation obtains real acknowledgements from the local mock service. Separate valid DRAFT products have no publication successes pre-recorded. The connected journey creates its order through the signed simulator UI and advances it through normal role-scoped commands and worker acknowledgements.
- API and the actual PostgreSQL polling worker run in test mode. All six destinations are pinned to mock mode at port 4102; actual Fynd connection is disabled. Private evidence files use the test-document directory, not presenter documents.
- Next builds and starts the real app with the test API rewrite and `.next-e2e` output. It does not overwrite the presenter's `.next` build. Next may regenerate its standard `next-env.d.ts`/TypeScript build references; the ordinary `pnpm build` restores normal generated references. Do not build both variants concurrently.
- Playwright runs serially with no retries and fresh browser contexts. API responses are validated by the serialized-response contract hook.
- On success/failure/interruption, the runner stops only the child process groups it started and releases its own lock. Diagnostic databases and test documents are retained; no database is automatically deleted. Hard termination can leave a lock/process: inspect the exact runner and ports before manually recovering, never remove a lock solely because it looks old.

`playwright-report/`, `test-results/`, `.local/` and `.next-e2e/` are ignored. Failed runs retain traces/screenshots; successful catalogue tests save `catalogue-publication.png` under their test-results folder. These artifacts can contain fictional login/session details and are not publication deliverables. No Git push or deployment is part of this command.

3. The real local worker obtains ERP first and then Fynd/SFCC acknowledgements. The browser waits for all three, verifies simulator storefront content and decoded uploaded pixels, and verifies the vendor sees the published, locked content. No publication completion flag or response is mocked by Playwright.
4. Vendor queues a local DAM source with three explicitly simulated failures. The real polling worker exhausts retries and dead-letters it; only ATI sees the replay control. Reasoned replay succeeds on attempt four, retains the job history and leaves the image PENDING on a draft. No browser test sets job status directly.

12. ATI rejects a partner exchange request with feedback. The partner sees the rejection, obtains a new quote and submits renewed terms. Failure/replay and assigned replacement cancellation/refund are integration-tested, not covered by this browser scene yet.

14. ATI starts another replacement checkout with a deliberately unavailable SFCC simulator, requests cancellation and sees stock remain reserved while acknowledgements are incomplete. Restoring/replaying the simulated integration obtains VOIDED payment and FENCED fulfilment evidence. The order is cancelled, reservations are released exactly once, no purchase/refund receipt is fabricated, and reload retains the original history.

## Scope still open

These tests are a starting acceptance suite, not the complete 35–45 minute runbook. Fresh invitation through activation, multi-product imports, actual external URL/DAM sources, partial-line source splitting, cancellation/rerouting, stock-disposition overrides/exchanges, reconciliation exceptions, every persona, all negative permissions, mobile/keyboard/accessibility, complete Arabic text and every failure/recovery path still need browser scenarios. Synthetic raster fixtures prove local upload/replacement, ZIP and simulated URL/DAM paths, not actual supplier connectivity or visual quality. External acknowledgement here means the local simulator only, never native Fynd access or real financial execution.
