# ATI ECS — requirement-by-requirement evidence

Baseline audit: 25 September 2026; updated through 29 September 2026. Scope: this `ecs-platform` implementation, not the older root static demo or the deployed Vercel site.

Authority: `the privately supplied Al_Tayer_ECS_CODEX_BUILD_SPEC.md`, especially §§1–16 and 19. The 54 IDs below preserve the source priorities: 52 Must Have and 2 Should Have. REQ-35 appears earlier in the source table but is numbered normally here. The source separates the original requirement from a proposed implementation; the latter is not evidence of a Fynd entitlement or delivered capability.

## Read this before presenting coverage

- **PARTIAL** means meaningful local implementation exists, but the complete source requirement or build-pack acceptance is not proven. It does not mean ready for deployment.
- **NOT_IMPLEMENTED** means the requested workflow is absent; neighbouring tables, fields, fixtures or UI labels do not count as implementation.
- No requirement is marked fully accepted. This is deliberately not a percentage-complete score. Each row must close its own gap and the cross-cutting gates below.
- Evidence links locate implementation and tests, not independent live-system certification. Integration tests exercise PostgreSQL and local mock adapters. Stub credentials, mock IDs and successful mock receipts are never real Fynd evidence.
- Fynd MCP configuration and loaded tools are verified, but authenticated tenant identity/access and ECS runtime credentials remain unverified. The isolated read-only probe does not connect business operations or enable the worker. SFCC, ERP/PIM, WMS, Finance and Logistics are also mocks.
- Keep two acceptance levels distinct: the local-demo goal can satisfy an external boundary with complete, contract-correct deterministic mock journeys; actual Fynd integration requires separate real-account proof. Missing live access must not be used to stop local work or to disguise missing local workflows. No row is fully accepted locally yet because its listed local work and/or applicable cross-cutting gates remain unproven.
- UI/browser evidence is recorded by date in [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). API tests do not replace browser acceptance, accessibility, Arabic or full actor journeys.

## Evidence maintenance

`pnpm requirements:validate` checks this register's structure, all 54 IDs, priorities, statuses and linked local evidence paths. It does **not** run acceptance tests or certify the requirements. Update the implementation, tests, corresponding row and remaining build plan together. A row becomes accepted only after its full source scope and applicable cross-cutting gates are evidenced; a green structural validator is not permission to relabel partial work.
